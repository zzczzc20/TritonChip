# Synthesis and PPA proxies

Generated by `make synth` (`flow/synth/synth.py`), Yosys 0.52, no PDK.

## What these numbers are, and are not

There is no process library in this repository, so nothing here is an area,
timing or power result. Three figures are reported:

| Metric | Definition | Good for | Not good for |
|---|---|---|---|
| **gates** | cell count after mapping to `AND/NAND/OR/NOR/XOR/XNOR/MUX/AOI/OAI` | comparing random logic between modules and across commits | anything storage-heavy; register files map to flops here but belong in SRAM macros |
| **depth** | longest topological path between registers, in gate levels (`ltp -noff`) | spotting structure that is deeper than it needs to be | an absolute delay number — see the calibration below |
| **flops** | sequential bits | sanity-checking that state matches the architectural spec | area, since flop area varies several-fold across cell flavours |

### Read `depth` against the calibration, not against a flat number

The generic gate set has **no carry-lookahead or parallel-prefix adder cells**,
so every addition maps to ripple carry and its depth grows linearly with width.
`flow/synth/calibration.v` measures that floor directly, and `make synth` prints
it above every run:

| reference structure | gates | depth |
|---|---:|---:|
| 32-bit adder | 154 | **32** |
| 64-bit adder | 303 | **64** |
| 89-bit adder | 478 | **71** |
| 24×24 multiplier | 2,964 | 50 |
| 32×32 multiplier | 5,377 | 65 |
| 16-to-1 × 32-bit crossbar | 571 | 5 |

A bare 32-bit addition already costs 32 levels here. **Any module containing
wide arithmetic is over a flat 50-level budget by construction**, and no amount
of pipelining will fix that, because the floor is the library's, not the
design's. A real standard-cell flow implements the same 64-bit addition as a
parallel-prefix tree at roughly logarithmic depth.

So the useful question is not "does this module clear 50?" but **"how far above
its own arithmetic floor does it sit?"** A module near its floor has no
structure left to fix with this library; a module several times above it does.
The report still flags 50 so the numbers stay comparable across commits, but the
flag is a pointer to this section, not a verdict.

### The generated datapath

These come from DSLX through Google XLS rather than from hand-written Verilog
(doc/xls.md), and XLS schedules them against its asap7 delay model at a 1300 ps
target. The stage counts are its answer, not a guess:

| Module | gates | flops | depth | floor | Assessment |
|---|---:|---:|---:|---:|---|
| `tnca_widen_xls` | 265 | 0 | 11 | — | combinational; any narrow format to binary32, no rounding to do |
| `tnca_widen_pair_xls` | 501 | 0 | 11 | — | two of the above |
| `tnca_narrow_xls` | 2,330 | 211 | 31 | 32 | **at the single-add floor**, across 3 stages |
| `tnca_cvt_xls` | 2,848 | 253 | 29 | 32 | at the floor, across 4 stages |
| `tnca_cvt_comb_xls` | 1,097 | 0 | 54 | 32 | the same DSLX unpipelined, one per lane in the vector FPU |
| `tnca_sfu_rcp_xls` | 11,669 | 330 | 42 | 50 | one 32×16 multiply per stage |
| `tnca_sfu_rsqrt_xls` | 20,223 | 428 | 41 | 50 | two coefficient tables, for even and odd exponents |
| `tnca_sfu_exp2_xls` | 14,946 | 529 | 69 | 50 | the multiply plus the exponent split |
| `tnca_sfu_log2_xls` | 13,246 | 447 | 72 | 50 | as above |
| `tnca_sfu` | — | — | — | — | the four above, one slice shared by all lanes |

Read against the combinational versions of the same modules, which is the
comparison that says what the scheduling did:

| Module | comb. depth | scheduled depth | comb. gates | scheduled gates |
|---|---:|---:|---:|---:|
| `tnca_narrow_xls` | 45 | **31** | 872 | 2,330 |
| `tnca_cvt_xls` | **54** | **29** | 1,097 | 2,848 |
| `tnca_sfu_rcp_xls` | **105** | **42** | 10,109 | 11,669 |
| `tnca_sfu_rsqrt_xls` | *yosys did not finish in 13 min* | 41 | | 20,223 |

`tnca_cvt_xls` was the one module over the 50-level flag that had nothing to do
with wide arithmetic — it is two conversions in series — and pipelining is what
fixed it. Its unpipelined sibling is over the flag for the same reason and is
used anyway: inside `tnca_vector_fpu` the clock is set by the FMA at 115
levels, so 54 is slack, and a pipelined instance would cost 253 flops per lane
to buy timing that unit cannot use. Both come from the same DSLX and
`tb_cvt_xls` checks both in one run.

**`tnca_cvt16_f32` is gone.** It converted FP16 and BF16 to binary32 at 140
gates and 14 levels — cheaper than `tnca_widen_xls` at 265 and 11, because it
did two formats where the generated one does four, and only in the widening
direction. It was deleted when the matrix unit and the vector FPU moved to the
generated pair: keeping two conversion implementations in agreement is the
cost the generator exists to avoid, and the surviving one is verified
exhaustively where this one was verified over 131,072 vectors. Its numbers
stay here as the comparison point.

`exp2` and `log2` remain over the flag at 69 and 72 levels, which is
one 32×16 multiplier in a library whose 32×32 multiplier is 65 levels by
itself; XLS's own estimate agrees, putting `exp2` at 1220 ps against a floor of
1217. Nothing is left there to restructure.

### What four fragment formats cost the matrix unit

`m.mma.async` went from two input formats to four — FP16 and BF16 plus both
OCP FP8 encodings — by replacing the hand-written `tnca_cvt16_f32` in front of
each MAC with `tnca_fpu_multi`, which is `tnca_widen_xls` in front of the same
binary32 FMA. The measurement is the point of doing it that way:

| | gates | flops | depth |
|---|---:|---:|---:|
| before: FP16 + BF16, hand-written converter | 316,846 | 135,731 | **190** |
| after: four formats, generated converter | 319,209 | 135,744 | **176** |

**Two extra formats cost 2,363 gates — 0.7 % — and the critical path got 14
levels shorter.** Both halves of that are worth stating.

The depth fell because the generated widening is shallower than the one it
replaced: `tnca_widen_xls` is 11 levels against `tnca_cvt16_f32`'s 14, and it
sits directly in the MAC's operand path.

The area barely moved because of something the structure paid for. Seventeen
`tnca_cvt16_f32` instances (2,380 gates) became thirty-two `tnca_widen_xls`
instances (8,480 if each were built), which should have cost about 6,100 more.
It did not, because sixteen of those widen the *same* A element with the same
inputs and yosys merged them. Writing the MAC as one multi-precision module
and instantiating it sixteen times reads as redundant and synthesises as
shared.

63 % of this module is still the accumulator file, which belongs in SRAM and
not in flops; that has not changed.

### One module this flow cannot measure

`tnca_vector_fpu` now holds sixteen FMAs, sixteen all-pairs converters and the
four-function SFU slice — about 180 k gates of deep muxing. **Yosys did not
finish mapping it in five and a half hours.** That is not a PPA result; it is a
fact about measuring this design with this flow, and it is recorded rather than
quietly dropped from the table.

Removing the SFU does not rescue it: `python3 flow/synth/synth.py
'tnca_vector_fpu@nosfu'` builds the unit with `HAS_SFU = 0`, which is a real
build parameter and not a measurement fiction, and that did not finish in
45 minutes either. (The `@` names a *configuration* of a top rather than a
different top, so the report can carry both rows without calling them the
same thing.)

So the parts are measured instead, and they are enough to read the whole: the
SFU slice as `tnca_sfu`, the converter as `tnca_cvt_comb_xls` (1,097 gates,
54 levels) and the FMA as `tnca_fp32_fma` (7,120 gates, 115 levels, and the
one that sets this unit's clock). Sixteen of the first two and sixteen of the
third is where the unit's area goes, and the FMA is where its depth goes.

What this is *not* is evidence about silicon. It is evidence that this
particular gate-level proxy flow has an upper size limit, and that the unit
has passed it.

`tnca_lsu`, `tnca_vector_rf`, `tnca_vector_alu` and `tnca_core` are long runs;
`make synth` regenerates the full table and `sim/build/synth.json` holds the
raw per-cell breakdown.

## What measuring changed

Four structures were rebuilt because the numbers said so. All four are §6.2 of
the architecture document applied literally: decide the arithmetic after looking
at what it costs.

### 1. Log-depth leading-one search and population count

Written the obvious way,

```verilog
for (i = 0; i < W; i = i + 1) if (v[i]) idx = W-1-i;   // W chained muxes
for (i = 0; i < W; i = i + 1) cnt = cnt + v[i];        // W chained adders
```

these are linear in width. At W = 89 the first was most of the FMA's critical
path; at VLEN = 16 the second was sixteen 32-deep carry chains in parallel.
`tnca_lzc` isolates the highest set bit with one subtract on the bit-reversed
input and converts the one-hot to binary with log₂W OR trees; `tnca_popc` is a
balanced adder tree. They cost 217 and 275 gates and 16 and 22 levels.

### 2. The scalar multiplier left the scalar ALU

| `tnca_scalar_alu` | gates | depth |
|---|---:|---:|
| with a combinational 64×64 multiplier | 28,035 | 135 |
| multiplier moved to `tnca_mul64` | **3,741** | **61** |

**−87 % area and −55 % depth**, and what remains is within three levels of the
library's 64-bit-adder floor. The scalar unit's actual job is address
arithmetic and loop counters (§11.3); it should not have been carrying an array
multiplier's cost on every instruction. `s.mul` and `s.mulh.*` now run on a
3-stage pipelined unit with their own latency, which the core's writeback
reservation schedules.

### 3. The FMA was cut into a pipeline

| `tnca_fp32_fma` | gates | flops | depth |
|---|---:|---:|---:|
| combinational | 6,781 | 0 | 207 |
| 2 register stages | 7,120 | 203 | **115** |

The cuts are placed either side of the two expensive things: the 24×24 multiply
and the align/add, then the normalise/round. 115 against an 89-bit-adder floor
of 71 means the remaining depth is mostly that adder. The 516 k-vector
differential test passes unchanged, and the testbench now streams vectors
back-to-back so the pipeline registers are exercised with a full pipe.

### 4. One multiplier per lane, one crossbar, one comparator

`v.mulh.s` and `v.mulh.u` were written as `$signed(x)*$signed(y)` and `x*y`,
which is two independent multiplier arrays per lane. The signed high half is
derivable from the unsigned product:

```
x_s * y_s = x*y - 2^N*(x[N-1] ? y : 0) - 2^N*(y[N-1] ? x : 0)   (mod 2^2N)
```

The correction terms are multiples of 2^N, so they touch only the high half and
cannot borrow out of the low half — two conditional subtractions replace an
entire array. The same pass replaced five shuffle crossbars (which differ only
in a source index) with one, and six comparator trees with one subtractor whose
borrow bit answers all of them.

| `tnca_vector_alu` | gates | depth |
|---|---:|---:|
| as first written | 205,205 | 102 |
| one multiplier per lane | 163,101 | 101 |
| + shared crossbar and comparator | **145,334** | **99** |

**−29 % for identical behaviour**, verified by the same 266 vector checks before
and after, and `t06_alu` covers the signed-high derivation with 186 randomised
cases weighted toward sign boundaries. The test was confirmed to fail when the
correction is removed.

## Remaining findings

### The register files must not stay as flops

`tnca_scalar_rf` is 31,033 gates for 8 kbit of state — the cost of three
asynchronous read ports built out of multiplexer trees. The vector file is the
same structure at 32 KiB in the reference configuration, which is not something
to build from flops at all.

§5.3 is explicit about the replacement: banked SRAM, 16 banks of 64 bit, 1R1W
each, with an operand-collector front end and a stated port budget, sized
*before* the arithmetic is sized. Until then the gate number for that module
should be read as "this is why the banked version exists", not as an estimate.

### The integer vector unit is still the largest block

Even after the rework it is larger than the entire 16-lane FP array, because
every operation is computed for every lane and selected at the end: the
shifters, `clz`, `popc` and the reduction tree all exist simultaneously. Next
reductions, in order of value:

1. one funnel shifter per lane serving all three shift directions, with left
   shift done by input and output bit reversal;
2. multi-cycle execution for the rare operations once the vector RF moves to
   banked SRAM with an operand collector, dropping them from the parallel array.

Neither changes the ISA.

### The accumulator file dominates the matrix unit, and it is flops

`tnca_matrix` is 316,846 gates, of which `tnca_acc_rf` alone is 200,381 --
**63% of the matrix unit is storage**, and the 16 MACs that do the arithmetic
are the smaller half. 131,072 flops is exactly the 16 slots x 16 rows x 16 lanes
x 32 bits the architecture specifies (§5.1), so the state is right; building it
from flops is not.

This is the same finding as the register files, and it lands harder here because
the accumulator is read and written every cycle of an MMA. §5.4 asks for the
accumulator to be reachable from the vector unit at row granularity, which is a
port requirement, not an area one — a banked SRAM with a row-wide port satisfies
it directly.

The 190-level depth is the FMA (115 on its own) plus the accumulator read and
the operand muxes in front of it. Both halves have the same fix: more pipeline
stages for the FMA, and a registered SRAM read for the accumulator.

### Walking the row base instead of recomputing it

`tnca_tensor` first computed each row's address as

```
base + (c0 + row)*stride0 + c1*stride1
```

which puts a 64x64 multiply in the inner loop of every transfer. Walking it
instead -- multiply once at setup, add `stride0` per row -- is what a DMA engine
is supposed to look like, and took the module from 89 to 83 levels.

The remaining 83 is the setup multiply itself, which is at the library's floor
for 64-bit multiplication and cannot go lower without pipelining it. The core
already contains a pipelined multiplier (`tnca_mul64`); reusing it for the setup
cycles is the obvious next step and costs only latency on a path that has none
to lose.

### What a real flow would have to confirm

Nothing here substitutes for static timing on a real library. The specific
claims that need checking first, in order:

1. that the FMA's align/add stage closes at the target frequency once the adder
   is a parallel-prefix tree rather than ripple carry;
2. that the banked vector RF's operand collector does not become the new
   critical path;
3. that the flop counts here (`tnca_mul64` at 768, `tnca_fp32_fma` at 203) are
   not hiding a register-heavy pipeline that a real area model would penalise;
4. that the accumulator file as banked SRAM still supports a row-wide read and
   write every cycle, which is what the matrix unit's loop order assumes.
