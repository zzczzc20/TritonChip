# Census: hybrid LSU, memory-side mux, command register, tensor/transfer engine (tile 0)

Source: /home/ubuntu/r42-wt/shrink rtl/core/*.v (read only), tile0_rel.txt, census/tile0_base.csv. "Attributed" = taken from the instance table or from RAM macro cells in the census (RAM64M8 = 8 LUT = 7 data bits x 64 deep, RAM32M16 = 8 LUT = 14 data bits x 32 deep; macro children not double counted). "Raw census" LUT = LUT1-6 cells grouped by the net they drive; they run 8-15% above the instance table (and 46% above on adapter/hybrid-self), so I scale: fast x0.92, slow unit x0.855, txf x0.852. Scaled raw numbers are "estimated" (net-name grouping, not per-operator reports).

## 0. Resolved parameters (arithmetic)
- PORT_TAG_W (multicore_shell:61) = 2 + clog2(LINE_SLOTS 64) = 8 = LSU_TAG_W. MTAG_W (core:1745) = 8-1 = 7. Hybrid BEAT_W 7, NT = 6, fast SLOTS = 1<<6 = 64. MEM_DW 512, MEM_BYTES 64. RCTX_W = 2 (NUM_RCTX 4). LSU_BEATS = 8 (top default; 8 < 1<<(8-3)=32 so unchanged); SLOW_UNITS = 1 (LSU_INFLIGHT 1).
- Slow pair/unit are NOT given MEM_DW (hybrid:145): defaults MEM_DW 64, MEM_BYTES 8, MEM_SHIFT 3, unit BEAT_W = 6-1 = 5, NUM_BEATS 8, VLEN 16, ELEN 32. tnca_lsu_bank.v is not instantiated (needs !HYBRID_LSU).
- txf (core:2128-2140): DESC_N 16 (core default :164), WIN_N 32, TAG_W 4, NTAG 16, NSLOT = 16/2 = 8, LINE_ENGINE 1, LSLOT_N = 1<<(7-1) = 64, CMD_N 8 (default), PTAG_W 7, PORT_DW 512, PORT_BYTES 64, MEM_DW 64 (TENSOR_DW), HAS_XPOSE 2, MUL_PIPE 1, XB 16, XR_MAX 16, BAR_W 3.
- command register width (core:1786) = 1321 + RCTX_W = 1323 bits (sum: 1+1+1+3+1+2+64+64+512+64+1+4+64+512+16+2+3+8).

## 6. Where I could not determine
- Why the census RAM for `d_base`, `d_e0-d_e2` stops at bit 55 (`d_e3/d_e4` have 64) and `d_boxel` has 14 of 21 bits, while the `t_*` FFs are full width: no RTL cause found.
- Why `d_dtype` is FF (128) and not LUTRAM: likely the second constant-index read `d_dtype[0]` in `_unused` (:1746); not verified.
- Merged RAM names: `ls_rctx`, `sl_keep` and fast `offset/size/signed_load/dst_class` do not appear by name; I assigned them to the macro that has matching bit counts (bits add up: fast 39 b in 6 macros, `ls_vreg` 10 b in 1+1 macros).
- Timing: no timing data was in what I read, so whether BRAM/DSP replacements meet 90-100 MHz is unknown. URAM288 read latency beyond "1 cycle" is not justified by the RTL; every extra cycle adds to slot occupancy and to completion latency in L1/T3.
- Census vs table LUT mismatch (hybrid-self+adapter 2,034 raw vs 1,091): cause not determined; I used table totals and raw cells only as weights.
