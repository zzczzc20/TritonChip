# Unmerged E4M3 descriptor-GEMM experiment

The existing descriptor GEMM planner accepted `e4m3` but code generation failed with `KeyError('e4m3')` for its tensor transfer. The isolated candidate accepts both E4M3 and E5M2 transfer aliases and selects K32 on DP E4M3 when K is a multiple of 32; it retains K16 on other sizes to avoid unverified signed-zero padding changes. This is not yet universal K32. Its partitioned variants use the planned K size but have not been run numerically.

The [DP TLM comparisons](k32_descriptor_tlm_20261031.tgz) first failed in both routes due to the independently fixed TNCA-IR AOT `imp` error. After that fix, the control uses the same corrected transfer code with `TNCA_FP8_FORCE_K32=0` and K16; the candidate uses K32. At 16×16×32, first finite-input launch had 3081 → 3197 cycles and 0.0126953125 → 0.01123046875 instructions/MAC. At 16×16×64 it had 3852 → 3929 cycles and 0.0078125 → 0.00634765625 instructions/MAC. Each used one launch, one code load before launch, zero loads during launch, and had 0/256 bit mismatches against independent DP arithmetic. A second NaN-input launch also matched 0/256 per route; its cycles were 1666 → 1639 and 2132 → 2034 respectively. These are uncalibrated TLM observations, not board results; finite first launches are cold and the NaN calls follow them. The original uncorrected source has no numerical control because it fails compilation.

The [default-code audit](k32_descriptor_audit_20261031.tgz) compared 113/113 unchanged, with zero changed or uncompared. Generic tail shapes, partitioned variants, model execution and board tests remain unverified; the candidate is not merged.
